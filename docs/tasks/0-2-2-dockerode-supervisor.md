# Задача 0.2.2 — Супервизор контейнера через Dockerode

> Эпик 0.2 · Фаза 0 · ✅ done · зависит от: 0.2.1, 0.1.2 · оценка: 4-5 ч

## Цель

Приложение при старте само проверяет Docker, поднимает контейнер базы, дожидается готовности и только затем запускает воркер.

## Контекст

Пользователь не должен помнить про `docker compose up`. Но Docker Desktop может быть не установлен, не запущен или занят — каждый из этих случаев требует своего внятного сообщения, а не падения с ошибкой подключения к базе.

## Что должно быть сделано

- Реализовать проверку доступности демона Docker через Dockerode
- Реализовать поиск контейнера проекта, его создание при отсутствии и запуск при остановленном состоянии
- Реализовать ожидание готовности по healthcheck с таймаутом и понятной ошибкой по его истечении
- Применить миграции Prisma после готовности базы
- Публиковать состояния запуска в поток событий IPC: демон недоступен, поднимаем, ждём готовности, применяем миграции, готово, ошибка
- Воркер стартует только после успешного завершения последовательности

## Критерии приёмки

- [x] Приложение запускается на машине с остановленным контейнером и поднимает его само
- [x] При выключенном Docker пользователь видит сообщение с указанием причины, а не пустой экран
- [x] Таймаут ожидания готовности не приводит к зависанию интерфейса
- [x] Повторный запуск приложения не создаёт второй контейнер

> Для второго критерия эта задача поставляет типизированное состояние ошибки через IPC; визуальное отображение этого состояния реализуется отдельно в `0.2.3`, как и предусмотрено границей задач.

## Подсказки

- Каждое состояние последовательности — отдельное событие; экран `0.2.3` их только отображает

## Не делать

- Не пытаться устанавливать Docker за пользователя
- Не реализовывать сам экран состояния — это задача `0.2.3`
