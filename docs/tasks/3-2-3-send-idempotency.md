# Задача 3.2.3 — Гарантия доставки уведомления

> Эпик 3.2 · Фаза 3 · ✅ done · зависит от: 3.2.2 · оценка: 2-3 ч

## Цель

Одно совпадение не теряется никогда и не дублируется при обычных повторах. В одном узком случае дубль допускается осознанно.

## Контекст

Здесь важно не пообещать невозможного. Bot API не принимает ключ идемпотентности от клиента: отправив запрос и не дождавшись ответа, приложение не может выяснить, приняла ли его удалённая сторона. Остаётся окно, в котором сообщение ушло, процесс упал до записи отметки, и после перезапуска ситуация неотличима от неотправленного.

Значит, выбор такой: либо при неопределённости не отправлять и иногда терять объявление, либо отправлять и иногда прислать дубль. Для монитора объявлений верно второе — **редкий дубль лучше молча потерянной находки**, ради которой всё и построено.

Поэтому гарантия здесь — устойчивая очередь и доставка не менее одного раза. Обычные повторы, ретраи и перезапуски дублей не создают; дубль возможен только в этом узком окне.

## Что должно быть сделано

- Использовать `Match.notifiedAt` как признак доставки
- Отметку писать сразу после подтверждения от Telegram, отдельной короткой транзакцией
- Ввести промежуточное состояние `sending` со временем начала: после перезапуска запись
  в нём считается неопределённой и отправляется повторно
- Записывать в журнал каждый случай повторной отправки из неопределённого состояния —
  так редкий дубль объясним, а не выглядит дефектом
- Покрыть интеграционными тестами: повторный запуск отправителя, падение до отправки,
  падение между отправкой и отметкой

## Критерии приёмки

- [x] Повторный запуск отправителя не создаёт дублей для доставленных совпадений
- [x] Падение до отправки приводит к доставке после перезапуска, а не к потере
- [x] Падение между отправкой и отметкой может дать один повтор — это ожидаемое поведение, зафиксированное в журнале
- [x] Ни один сценарий не приводит к потере совпадения
- [x] Интеграционные тесты на все три сценария зелёные

## Результат

- `Match.notifiedAt` остаётся финальным durable-признаком доставки, а `notificationSendingAt` хранит начало внешнего Telegram side effect до подтверждения.
- Перед отправкой delivery atomically фиксирует `sending`; после подтверждения `markNotified` одной короткой записью устанавливает `notifiedAt` и очищает `notificationSendingAt`.
- После перезапуска уже доставленный Match не отправляется повторно; Match в persisted `sending` считается неопределённым и безопасно отправляется ещё раз.
- Повтор из неопределённого состояния фиксируется стабильным journal-сообщением `Telegram notification resent from uncertain state`.
- Узкое окно после Telegram acceptance и до `notifiedAt` намеренно остаётся at-least-once: возможен один объяснимый дубль, но совпадение не теряется.
- PostgreSQL integration покрывает restart после подтверждённой доставки, crash после durable marker до send и crash после Telegram acceptance до финальной отметки; отдельный pg-boss integration подтверждает durable outbox через process/database recreation.
