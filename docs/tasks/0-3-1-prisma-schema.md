# Задача 0.3.1 — Схема Prisma по доменной модели

> Эпик 0.3 · Фаза 0 · ✅ done · зависит от: 0.2.1 · оценка: 3-4 ч

## Цель

Описать в Prisma все сущности MVP-1 в соответствии со спецификацией доменной модели.

## Контекст

Схема — общий язык всех последующих фаз. Отклонения от спецификации здесь расходятся волной по всему коду, поэтому решения из спеки (глобальный `Listing`, идентификатор площадки как первичный ключ, состояние вместо флагов, цена как пара «вид + сумма») переносятся буквально.

При этом создаются только сущности, нужные срезу MVP-1. Пять оставшихся таблиц до первого уведомления не используются ни разу, и заводить их заранее значит переносить работу будущих срезов в фундамент — ровно то, из-за чего первая пользовательская ценность отодвигается.

## Что должно быть сделано

- Описать сущности среза MVP-1: `Monitor`, `MonitorCursor`, `Run`, `Listing`, `Match`, `Setting`
- Остальные сущности (`Favorite`, `PriceSnapshot`, `SellerBlock`, `HealthEvent`,
  `SchemaSnapshot`) в этой миграции не создаются: они приходят в `0.3.4` вместе
  со своими срезами
- Использовать идентификатор площадки как первичный ключ `Listing` —
  **при условии, что разведка `1.0.2` подтвердила его глобальную уникальность**
- Состояния монитора и избранного описать перечислениями, не булевыми флагами
- Поля `query`, `keywords`, `raw`, `details`, `fields` — как `Json`
- Сгенерировать первую миграцию и проверить её применение на чистой базе

## Критерии приёмки

- [x] Миграция применяется на пустой базе без ошибок
- [x] Модель соответствует `docs/superpowers/specs/data-model.md` по полям описанных сущностей
- [x] Цена описана как `priceKind` + nullable `priceAmount`
- [x] Состояние обхода лежит в `MonitorCursor`, а не в полях `Monitor`
- [x] Клиент Prisma генерируется, типы доступны в общем модуле

> `Favorite` намеренно не создаётся в этом срезе, поэтому его состояние также не материализуется раньше `0.5.0`; это следует явному порядку появления таблиц из `data-model.md`.

## Подсказки

- Спецификация: `docs/superpowers/specs/data-model.md`
- Схема создаётся в срезе `0.1.0`, то есть раньше живой разведки `0.2.0`. Часть
  решений держится на непроверенных свойствах ответа площадки, поэтому правка
  схемы после разведки — не переделка, а запланированный шаг. Миграцию до MVP
  можно менять свободно

## Не делать

- Не добавлять сущности под Post-MVP (переписка, таксономия категорий)
- Не создавать индексы — это задача `0.3.2`
