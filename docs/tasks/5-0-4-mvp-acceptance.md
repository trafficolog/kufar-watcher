# Задача 5.0.4 — Приёмка среза MVP-1

> Эпик 5.0 · Фаза 5 · ⬜ todo · зависит от: 5.0.3, 5.0.2, 3.2.3 · оценка: 2-3 ч

## Цель

Пройти два сквозных сценария на реальных request-buildable ссылках — один для
«Игры и приставки» в Минске и один для покупки квартир в Минске — и
зафиксировать, что весь заявленный MVP perimeter готов.

## Контекст

Точка, ради которой строился весь срез. Приёмка проверяет не отдельные задачи, а то, что цепочка работает целиком в руках пользователя, а не в тестах.

Релиз `1.0.0` гарантирует два подтверждённых URL shape, которые проходят полную
production-цепочку `parse → route → build API request`:

- `kufar.by` / `www.kufar.by` + `r~minsk` + `igry-i-pristavki`, без operation и
  дополнительных path filters; текстовый `q~...` допустим;
- `re.kufar.by` + `minsk/kupit/kvartiru`, без дополнительных path filters и без
  search query.

Названия adapter kinds `electronics` и `real-estate` не означают поддержку всей
электроники или всей недвижимости. URL, который только успешно маршрутизируется,
но не имеет подтверждённого `buildKufarApiUrl()` mapping, не входит в acceptance
perimeter.

## Что должно быть сделано

- Пройти сценарий вручную на чистом профиле данных приложения (пустая база,
  пустое хранилище секретов): ввести токен, привязать чат, создать один монитор
  по Minsk `igry-i-pristavki` URL и один по Minsk `kupit/kvartiru` URL,
  дождаться нового объявления в каждом сценарии, получить уведомление и открыть
  его кнопкой
- Использовать подтверждённые acceptance examples:
  `https://www.kufar.by/l/r~minsk/igry-i-pristavki/q~ps5` и
  `https://re.kufar.by/l/minsk/kupit/kvartiru`; замена ссылки допустима только
  если CanonicalQuery сохраняет тот же request-buildable shape
- Проверить холодный старт для обоих поддерживаемых shape: создание каждого
  монитора не порождает пачку уведомлений о старых объявлениях
- Проверить перезапуск приложения с обоими активными мониторами: расписания
  восстанавливаются, ни одна находка не потеряна
- Оставить два монитора на несколько часов — ровно по одному на каждый из двух
  request-buildable shape — и сверить полученные уведомления с соответствующей
  выдачей вручную
- Записать результат в чек-лист приёмки отдельно по каждому shape и завести
  карточки на найденные дефекты

## Критерии приёмки

- [ ] End-to-end сценарий полностью проходится без обращения к базе и файлам
      отдельно для Minsk `igry-i-pristavki` и отдельно для Minsk
      `kupit/kvartiru`
- [ ] За время наблюдения нет пропусков ни у одного из двух мониторов
- [ ] Дубли, если появились, объяснимы записью в журнале о повторной отправке из неопределённого состояния
- [ ] Перезапуск приложения не нарушает работу ни одного из двух активных
      мониторов
- [ ] Чек-лист содержит использованные реальные ссылки и отдельный результат по
      каждому из двух request-buildable URL shape; дефекты заведены
- [ ] Результат приёмки не расширяет обещание поддержки на electronics вне
      Минска, `igry-i-pristavki` без `r~minsk`, rental `snyat/kvartiru`,
      `/elektronika`, `doma` или другие неподтверждённые semantics

## Не делать

- Не проверять тихие часы, сон машины, избранное и цены: они не входят в этот срез
- Не проверять установку на чистой машине: установочных пакетов до `5.7` не существует
- Не автоматизировать этот прогон: e2e-сценарии — задача `5.6.1`
- Не подменять acceptance URL ссылкой, которая лишь парсится/маршрутизируется,
  но приводит к `unsupported-api-mapping` на request-builder boundary
- Не экстраполировать успешную приёмку двух shapes на всю электронику, всю
  недвижимость или другие категории Kufar; категория «Авто» явно вне периметра
