# Задача 1.2.1 — Глобальный лимитер с джиттером

> Эпик 1.2 · Фаза 1 · ✅ done · зависит от: 0.1.2 · оценка: 3-4 ч

## Цель

TDD. Один лимитер на весь процесс, через который проходят все исходящие запросы к площадке.

## Контекст

Пять мониторов, канарейка и часовой чекер цен обращаются к одному и тому же сайту. Без общего лимитера они рано или поздно совпадут по времени и создадут всплеск. Джиттер нужен, чтобы обходы не выстраивались в идеально периодический рисунок.

## Что должно быть сделано

- Сначала тесты на виртуальных таймерах: соблюдение минимального интервала, очередь при конкурентных вызовах, применение джиттера
- Реализовать лимитер с настраиваемым минимальным интервалом и диапазоном джиттера
- Обеспечить единственный экземпляр на процесс воркера
- Значения по умолчанию взять из спецификации контракта площадки

## Критерии приёмки

- [x] При десяти одновременных вызовах запросы уходят последовательно с соблюдением интервала
- [x] Джиттер попадает в заданный диапазон
- [x] Тесты не зависят от реального времени
- [x] `1.2.1` предоставляет единый worker singleton и FIFO queue boundary; технический запрет обхода через неограниченный HTTP-путь завершается задачей `1.2.2`, где появится сам сетевой клиент

## Результат — 2026-09-07

- `RateLimiter` сериализует все запланированные операции FIFO с `concurrency=1`.
- Между стартами применяется `minIntervalMs + jitter`; production defaults дают общий темп `2–5` секунд для всех Kufar-хостов.
- `kufarRateLimiter` — единый module-level singleton worker-процесса для будущего HTTP-клиента `1.2.2`.
- Unit-тесты используют Vitest fake timers и не зависят от реального времени; отказ одной операции не ломает очередь.
