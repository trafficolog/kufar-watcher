# AGENTS.md — инструкция для AI-агентов (Kufar Monitor)

> Читают все AI-агенты при старте сессии (Codex Desktop, Cursor IDE, Claude Code).

## Цель проекта

Персональное десктопное приложение, которое следит за отфильтрованными выдачами
kufar.by по нескольким независимым правилам и присылает новые объявления в
Telegram. Один пользователь, одна машина, порядка пяти правил.

## Архитектурные принципы (нерушимые)

1. **Масштаб — пять мониторов, а не пятьсот.** Любая оптимизация, усложняющая
   код ради нагрузки, которой не будет, отклоняется. Пропускная способность
   системы заведомо избыточна для задачи; ценность в надёжности и предсказуемости.
2. **Spec-Driven Development.** Каждая задача начинается с карточки в
   `docs/tasks/`. Без карточки код не пишется.
3. **Вежливость к площадке — часть контракта.** Все исходящие запросы проходят
   через единый лимитер с джиттером. Обход технических ограничений площадки,
   ротация адресов, подмена отпечатков, параллельные обходы в несколько потоков —
   вне периметра проекта. Если площадка начинает отдавать ошибки, правильная
   реакция — снизить темп и сообщить пользователю, а не пробиваться.
4. **Анонимность по умолчанию.** MVP работает без входа в аккаунт. Авторизация
   появится только вместе с мессенджером, это Post-MVP (см. `superpowers/specs/deferred-requirements.md`).
5. **Система не чинит себя сама.** Автоматическая правка селекторов и парсеров
   вне периметра. Реакция на проблему зависит от её вида, и это различие
   принципиально:
   - **временный сбой** (сеть, таймаут, `5xx`) — ретраи, при необходимости
     работа через фолбэк, событие в журнал;
   - **`429`, ограничение темпа** — отдельный случай: увеличить паузу, снизить
     частоту, записать событие здоровья. Фолбэк здесь запрещён: переход на
     другой канал ради продолжения запросов — это и есть обход ограничения,
     которое площадка только что выставила;
   - **дрейф схемы** (структура ответа изменилась) — монитор в паузу и отчёт
     пользователю, без попыток продолжить.
   Смешивать их нельзя: в первом случае пауза остановит мониторинг из-за
   пятиминутного сбоя, во втором продолжение работы даст неверные данные.
6. **Честность важнее тишины.** Если обход не состоялся (сон машины, ошибка
   сети, пауза по дрейфу), пользователь должен об этом узнать. Молчащий
   монитор, который выглядит рабочим, — худший из возможных дефектов.

## Стек (не менять без согласования)

См. таблицу в `docs/ROADMAP.MD`. Ключевое: Electron + Vue 3, Postgres 16 в
Docker под Dockerode, Prisma, pg-boss, grammY на long-polling, undici.

Нативные модули (node-gyp, биндинги) запрещены: они ломают сборку Electron.
Для морфологии брать чистый JS.

## Хостинг и целевые платформы

Локальная машина пользователя, **Windows и Linux**. Приложение стартует вместе
с системой свёрнутым в трей и продолжает работать при закрытом окне. VPS,
облако, вебхуки и любые внешние сервисы не используются.

Платформенные различия, которые нельзя игнорировать:

- **Автозапуск.** На Windows работает штатный механизм Electron; на Linux нужен
  файл автозапуска в каталоге пользовательской автозагрузки. Реализация разная,
  поведение обязано быть одинаковым.
- **Трей.** На Linux доступность значка зависит от окружения рабочего стола.
  Приложение обязано оставаться управляемым, если значок недоступен.
- **Docker.** На Windows это Docker Desktop поверх WSL2, подключение через
  именованный канал; на Linux — сокет демона. Слой Dockerode должен выбирать
  транспорт по платформе.
- **Пути.** Каталоги данных и конфигурации получать через API Electron, никаких
  собранных вручную путей.

## Структура работы

Все задачи — в `docs/tasks/N-M-K-*.md`. Каждая карточка: цель, контекст, что
сделать, критерии приёмки, подсказки, «не делать». Порядок — в `docs/ROADMAP.MD`.

Процессная модель: `main` (окно, трей, жизненный цикл, Dockerode) ↔
`utilityProcess` воркер (планировщик, сеть, матчинг, Telegram) ↔ `renderer`
(Vue 3). Тяжёлое никогда не выполняется в `main`.

## Интерфейс

Прототипы в `prototypes/` — спецификация вида и поведения, а не исходный код.
Разметку и скрипты оттуда переписываем на компоненты; решения, состояния и
формулировки сохраняем как есть.

- Renderer — Nuxt 4 с `ssr: false`. Nitro и внутренний HTTP-слой не заводим:
  между Vue и службами приложения только типизированный IPC.
- Мост публикует API уровня продукта (`monitors.archive(id)`), а не уровня
  хранилища (`db.update('Monitor')`). Сырой `ipcRenderer` наружу не отдаётся.
- Данные площадки недоверенные. `v-html` для заголовков, описаний и имён
  продавцов запрещён.
- Доменный статус и состояние операции — разные поля. Смешивать `'drifted'` и
  `'loading'` в одном значении нельзя.
- Обратимое действие выполняется сразу и сопровождается отменой; подтверждение
  остаётся только для необратимого. Тост с отменой не гаснет по таймеру.

Полностью: `superpowers/specs/ui-architecture.md` и `ui-states.md`.

## Code style

TypeScript strict, никаких `any` в доменном коде. ESLint + Prettier. Имена
файлов kebab-case, типы PascalCase. Доменные модели описываются один раз и
переиспользуются между процессами через общий пакет типов.

## Безопасность

Токен бота вводится пользователем в настройках приложения и хранится локально в
защищённом хранилище учётных данных операционной системы, а не в файле рядом с
кодом.

**Оговорка по Linux, которую нельзя игнорировать.** Штатное защищённое хранилище
Electron на Linux опирается на системный сервис секретов, и если подходящего
бэкенда нет, оно молча деградирует до варианта без реального шифрования.
Приложение обязано проверять, какой бэкенд выбран, и различать два исхода:
защищённое хранилище доступно — сохраняем; недоступно — сообщаем пользователю
прямо и предлагаем осознанный выбор, а не записываем токен в незащищённое
хранилище под видом защищённого. Обещать пользователю защиту, которой нет, хуже,
чем честно сказать о её отсутствии. `.env` допустим только в режиме разработки. Бот обязан игнорировать любые
сообщения и нажатия кнопок от чатов, кроме привязанного. Параметры БД — в `.env`,
в git не попадают. `contextIsolation`
включён, `nodeIntegration` выключен, окно в песочнице, весь доступ из renderer
только через типизированный IPC-мост. Дополнительно обязательны: политика
содержимого, запрет перехода на внешние адреса внутри окна, запрет новых окон,
проверка отправителя в каждом обработчике IPC. Внешние ссылки открываются по
идентификатору объявления, а не по переданному адресу. Шрифты и прочие сторонние
ресурсы в сборке лежат локально, не подгружаются из сети. Полный перечень
требований — в `security/README.md`. Ответы площадки считаются недоверенными данными:
валидировать перед записью, не подставлять в HTML без экранирования.

## Терминология

**Срез поставки** — единица выпуска (`0.3.0`, `0.4.0`, …), задаёт порядок работ.
**Фаза** — тематическая группировка эпиков, порядка работ не задаёт.
**MVP-1** — конкретный срез `0.3.0`, и ничто иное: ссылка, интервал, простые
ключевые слова, уведомление в Telegram.
**Post-MVP** — всё, что вынесено за пределы среза `1.0.0`. Никогда не называть
это «фазой 2»: Фаза 2 в этом дереве существует и означает правила и планировщик.

## Что НЕ делать

Отложено осознанно (Post-MVP):

- Конструктор фильтров по таксономии категорий — только вставка готовой ссылки.
- Регулярные выражения в ключевых словах — только слова и glob-маски.
- ИИ-агент переписки с продавцом и любая работа с мессенджером Kufar.
- Категория «Авто» — только электроника и недвижимость.
- Любые площадки, кроме kufar.by.
- Фотографии в уведомлениях — сообщения текстовые.
- Проба через `/count` перед обходом и адаптивные интервалы: при пяти мониторах
  и минутном шаге это лишние состояния. `/count` используется только для
  предпросмотра при сохранении правила — и показывает счёт площадки **до**
  применения локальных фильтров, о чём интерфейс обязан сказать прямо.
- Антиспам-предохранитель на всплеск находок.
- Автоматическое восстановление после дрейфа схемы.

## Workflow задачи

1. Прочитать карточку задачи и связанный spec.
2. Если карточка помечена TDD — тесты сначала.
3. Реализовать минимально достаточно.
4. Прогнать тесты.
5. Обновить `status` карточки → `done`, при необходимости `sync_state: aligned`.
6. `npm run docs:ops:refresh && npm run docs:ops:check`.
7. Передать оркестратору на code review.
