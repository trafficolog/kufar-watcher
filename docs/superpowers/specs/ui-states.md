# Spec — состояния интерфейса

Два набора состояний, которые нельзя смешивать. Их путаница — самая частая
причина компонентов, в которых невозможно разобраться.

```ts
type HealthTone = 'ok' | 'warning' | 'error' | 'muted'   // доменный статус
type AsyncState = 'idle' | 'loading' | 'success' | 'error' // состояние операции
```

`monitor.status = 'drifted'` — это домен. `monitorEditor.saveState = 'loading'` —
это операция. Одно поле, хранящее и то и другое, рано или поздно окажется в
состоянии, которого не должно существовать.

## Канонический ответ на действие

| Действие | Ответ |
|----------|-------|
| Обратимое | выполняем сразу + тост с отменой |
| Необратимое | подтверждение до выполнения, с перечислением того, что исчезнет |
| Обычная настройка | автосохранение + тихое подтверждение |
| Секрет, файл, разрушающее | явное действие, без автосохранения |

Подтверждение на каждое действие — антипаттерн: оно обесценивает подтверждение
там, где оно действительно нужно. Отмена уместнее вопроса ровно до тех пор, пока
откат возможен.

**Тост с отменой не исчезает по таймеру.** Иначе единственный способ откатиться
пропадает, пока человек читает. Само гаснет только то, что ничего не требует.

## Редактор правила

| Состояние | Что видно |
|-----------|-----------|
| `existing/clean` | обычный редактор, «Отменить» недоступна |
| `existing/dirty` | метка «есть несохранённые изменения», «Отменить» активна |
| `new` | пустые поля, кнопка «Создать», счётчик приглушён |
| `url/checking` | «Проверяю ссылку на площадке…» |
| `url/valid` | категория, регион, тип продавца |
| `url/invalid` | ошибка с указанием, что именно не так |
| `url/unreachable` | «Сейчас проверить не удалось» — сохранять **можно** |
| `saving` | кнопка отключена и подписана «Сохраняю» |
| `save/error` | стойкий алерт, значения в форме сохранены |
| `drifted` | редактор плюс предупреждение об остановке |
| `archived` | редактирование недоступно, доступен возврат |

Отдельно про `url/unreachable`: недоступность площадки — не ошибка
пользователя, и блокировать сохранение из-за неё нельзя. Разбор уточнится при
первом обходе.

## Telegram

```
TOKEN_EMPTY → TOKEN_CHECKING → TOKEN_INVALID
                             → TOKEN_VALID → CHAT_UNBOUND
                                           → CHAT_WAITING_FOR_MESSAGE
                                           → CHAT_BOUND
```

Идентификатор чата пользователь не ищет руками: приложение ждёт сообщение боту и
находит чат само. Состояние ожидания обязано быть видимым, иначе шаг выглядит
сломанным.

## Режим источника данных адаптера

```ts
mode: 'primary' | 'fallback' | 'paused'
```

Без этого поля деградация невидима: фолбэк работает, находки приходят, и человек
не знает, что состав полей стал беднее. Режим показывается на карточке
подсистемы в «Здоровье» и коротко на доске, подробности — по ссылке.

Различение остаётся тем же, что в контракте площадки: временный сбой лечится
запасным каналом, дрейф схемы — паузой.

## Первый запуск

Доска с нулями не объясняет, что делать. При отсутствии правил тот же маршрут
показывает состояние первого запуска: два шага, Telegram и первое правило.
Отдельного `/onboarding` нет — вторая навигационная система обошлась бы дороже.

## Запуск приложения

До появления страниц Nuxt приложение поднимает Docker, ждёт базу, применяет
миграции, стартует планировщик и читает секреты. Это не маршрут, а
`AppBootScreen.vue` поверх окна: список шагов с отметками, при успехе исчезает
за секунду, при отказе показывает причину и три выхода — повторить, открыть
журнал, выйти.

## Общие состояния экранов

Каждый экран со сбором данных обязан иметь все четыре: `loading` (форма
содержимого, не пустота), `empty` (объяснение и путь дальше), `recoverable
error` (что случилось и как повторить), `fatal error` (что сломано и куда
смотреть).
