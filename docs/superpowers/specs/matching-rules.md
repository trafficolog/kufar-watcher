# Spec — правила отбора объявлений

## Порядок применения

Фильтры применяются в порядке возрастания стоимости, чтобы не платить за
запросы, результат которых всё равно будет отброшен:

1. **Параметры запроса** — то, что площадка отфильтрует сама (категория, регион,
   тип продавца, поисковая строка из ссылки).
2. **Водяной знак** — отбрасываем уже виденное.
3. **Чёрный список продавцов** — постфильтр по идентификатору аккаунта.
4. **Ключевые слова по заголовку** — бесплатно, данные уже есть.
5. **Ключевые слова по описанию** — если в правиле включён поиск по описанию,
   описание загружается для каждого нового объявления, дошедшего до этого шага.
   Стоит одного дополнительного запроса на объявление.

Соблазнительная оптимизация «совпало по заголовку — описание не грузим» здесь
неверна, и это стоит объяснить, потому что выглядит она разумно. Описание нужно
не только для вердикта: если ключевое слово встречается в описании, его фрагмент
уходит в уведомление. Пропустив загрузку при совпадении по заголовку, мы теряем
фрагмент, который пользователь просил показывать. Дополнительный запрос на
объявление — осознанно принятая цена этой возможности.

## Нормализация текста

Перед любым сопоставлением и заголовок, и термы приводятся к одному виду:
нижний регистр, `ё` → `е`, схлопывание пробелов, отсечение пунктуации по краям
токена. Нормализация обязана быть одинаковой для обеих сторон сравнения —
это самый частый источник «почему не сработало».

В текущем срезе действует явный контракт: **один term = один нормализованный
token**. После нормализации term, который даёт ноль токенов или больше одного
токена, считается ошибкой конфигурации. Поэтому `playstation 5` не является
фразовым поиском и отклоняется, а не превращается в matcher, который молча
никогда не сработает.

Краевая пунктуация term и token обрабатывается симметрично: `(ps5)` и `ps5`
эквивалентны. Символ `*` — исключение из удаления краевой пунктуации: он
сохраняется как glob-оператор, поэтому `playstation*`, `*pro` и внутренние
маски продолжают работать по прежнему контракту. Это же правило должно быть
видно в будущей UI-подсказке редактора термов.

## Маска против морфологии

Ключевое правило, принятое на этапе проектирования:

Правило зависит от среза, и это надо читать внимательно, потому что до `0.4.0`
и после него поведение разное:

| Терм | MVP-1 (`0.3.0`) | С `0.4.0` |
|------|-----------------|-----------|
| содержит `*` | glob-маска, буквально | glob-маска, буквально, **морфология отключена для этого терма** |
| не содержит `*` | нормализованное точное совпадение | стеммится вместе с текстом |

`playstation*` находит `playstation`, `playstation5`, `playstationa` в обоих
срезах. `колонка` в MVP-1 находит только `колонка`, а с `0.4.0` — ещё `колонки`,
`колонкой`, `колонок`.

Маска и морфология несовместимы на одном терме принципиально: стеммер режет
окончание, а `*` его как раз и заменяет, поэтому вместе они дают ложные
срабатывания.

Правило должно быть видно пользователю в подсказке редактора правила, иначе
поведение выглядит случайным.

Реализационно это два эпика: `2.1` даёт нормализацию, маски и интерфейс
сопоставления с одной реализацией; `2.6` добавляет вторую реализацию со
стеммером и правило выбора. Вызывающий код при переходе не меняется.

## Стеммер (с среза `0.4.0`)

Чистый JavaScript, алгоритм Портера для русского. Нативные биндинги запрещены:
они ломают сборку Electron. Стеммер применяется к отдельному токену, а не к
строке целиком.

Известное ограничение, которое принимаем: стеммер Портера не знает
словоформ-исключений и иногда сводит разные слова к одной основе. Для задачи
«не пропустить объявление» это приемлемо — ложное срабатывание дешевле пропуска.

## Include и exclude

- Список `include` пуст → проходят все объявления (правило работает как чистый
  мониторинг ссылки).
- Список `include` непуст → нужно совпадение хотя бы по одному терму.
- Совпадение по любому терму из `exclude` → объявление отбрасывается, даже если
  сработал `include`.
- `exclude` проверяется по тем же полям, что и `include`.
- Каждый элемент обоих списков обязан соблюдать один и тот же single-token
  compiler contract; отдельной более мягкой семантики для `exclude` нет.

## Фрагмент для уведомления

Матчер возвращает не только вердикт, но и найденные термы с позициями. Если
совпадение нашлось **в описании, а не в заголовке**, в уведомление добавляется
фрагмент текста вокруг совпадения — иначе пользователю непонятно, почему
объявление вообще пришло.

## Что вне периметра MVP-1

Регулярные выражения, phrase search, взвешивание термов, поиск по значениям
категорийных параметров, нечёткое сопоставление и опечатки. Морфология в срез
MVP-1 (`0.3.0`) тоже не входит — она приходит срезом `0.4.0`; в MVP-1 работают
простые слова и маски.
