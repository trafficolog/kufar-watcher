# Release process — Kufar Monitor

Релизная единица проекта — **срез поставки** из `docs/ROADMAP.MD`, а не отдельная
task-карточка. Обычная задача проходит `branch → PR → green CI → merge`, но тег
на неё не ставится.

## Версии

До `1.0.0` номера версий следуют delivery slices из ROADMAP:

- `0.1.0` — Фундамент;
- `0.2.0` — Контракт площадки;
- `0.3.0` — MVP-1;
- `0.4.0` — Комфорт;
- `0.5.0` — Накопленные данные;
- `0.6.0` — Устойчивость;
- `1.0.0` — первый полноценный пользовательский релиз.

После `1.0.0` используется обычный SemVer: breaking change → major, feature →
minor, fix → patch. Patch-версии до `1.0.0` (`0.2.1`, `0.2.2`, …) выпускаются
только для исправления уже выпущенного среза, а не после каждой задачи.

## Release gate

Когда закрыт весь срез поставки:

1. Убедиться, что все входящие в срез task-карточки завершены и docs-ops
   синхронизирован.
2. Выполнить полный verification pipeline: tests, typecheck, lint, formatting,
   PostgreSQL integration, build и применимые Electron smoke checks.
3. Обновить `version` в `package.json` и корневые version-поля в
   `package-lock.json` одной и той же версией.
4. Сделать отдельный release PR `chore(release): X.Y.Z` без функциональных
   изменений.
5. После green CI смержить release PR.
6. Поставить **annotated tag** `vX.Y.Z` на exact merge commit release PR. Тег
   после публикации не перемещать и историю не переписывать.
7. Создать GitHub Release из этого тега и использовать проверенные release notes.

## Release notes

Release notes должны содержать:

- что появилось в срезе;
- существенные контракты/ограничения;
- результат verification;
- известные ограничения;
- наличие или отсутствие бинарных assets.

До появления packaging в соответствующем срезе releases являются честными
source/development milestones. Фиктивные Windows/Linux binaries не прикладывать.

## Исторические релизы

Если release cadence вводится после уже закрытого среза, разрешено поставить тег
ретроспективно на фактический проверенный checkpoint. Нельзя создавать новый
коммит задним числом, переписывать историю или переносить task-коммиты ради
красивого тега.
