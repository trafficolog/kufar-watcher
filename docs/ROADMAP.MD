# ROADMAP — Kufar Monitor

> Тактический план: срезы поставки, порядок эпиков, вехи.
> Продуктовые решения и их обоснование — в `superpowers/specs/`.

## Фазы против срезов поставки

**Фазы — тематическая группировка, а не порядок работ.** Порядок работ задают
срезы поставки ниже. Это важно: если идти строго по фазам, первое уведомление в
Telegram появится только после трёх полностью закрытых фаз, и до этого момента
у системы нет ни одного пользовательского свойства. Срез MVP-1 нарезан поперёк
фаз так, чтобы цепочка «ссылка → площадка → отбор → Telegram» замкнулась как
можно раньше.

## Канонический стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Рантайм | Node 22, TypeScript strict | — |
| Десктоп | Electron + electron-vite | приложение живёт на машине пользователя, работает из трея |
| Целевые ОС | **Windows и Linux** | сборки, автозапуск и трей проверяются на обеих |
| UI | Nuxt 4 в режиме SPA (`ssr: false`) + Vue 3 + Pinia | маршруты, автоимпорт и слои из коробки; сервер рендерить нечего |
| Мост процессов | `contextBridge`, узкий API по сценариям | renderer не знает Prisma и не получает сырой `ipcRenderer` |
| БД | PostgreSQL 16 в Docker | выбрано пользователем на этапе опроса из четырёх вариантов, включая SQLite |
| ORM | Prisma | миграции и типизация |
| Очереди/расписания | pg-boss | следствие выбора Postgres, а не его причина |
| Управление Docker | Dockerode | автоподъём контейнера БД при старте приложения |
| HTTP | undici | нативный keep-alive, таймауты, пул соединений |
| Telegram | grammY (long-polling) | статического адреса нет, webhook невозможен |
| Морфология | чистый JS-стеммер Портера для RU | нативные биндинги запрещены (electron-rebuild) |
| Тесты | Vitest, Playwright (Electron e2e) | — |

## Срезы поставки

| Срез | Эпики | Что появляется |
|------|-------|----------------|
| `0.1.0` **Фундамент** | 0.1, 0.2, 0.3.1–0.3.3, 0.4 | приложение стартует, БД поднимается сама, схема MVP применена |
| `0.2.0` **Контракт площадки** | 1.0 | реальные ответы Kufar сняты в фикстуры, гипотезы контракта подтверждены или опровергнуты |
| `0.3.0` **MVP-1 — вертикальный срез** | 1.1, 1.2, 1.3.1–1.3.3, 1.4, 2.1, 2.2, 2.4, 3.1, 3.2.1–3.2.3, **5.0**, 5.8.2 | ссылка + интервал + простые ключи и маски → уведомление в Telegram, создаваемое и настраиваемое из окна приложения |
| `0.4.0` **Комфорт** | 0.3.4, 1.5, 2.3, 2.5, 2.6, 3.3 | морфология, поиск по описанию, фильтр продавца, тихие часы, догоняющий обход после сна |
| `0.5.0` **Накопленные данные** | 0.3.5, 3.2.4, 3.4, 5.3, 5.4 | избранное и кнопка «В избранное», история цен, лента, архив, экспорт и восстановление |
| `0.6.0` **Устойчивость** | 0.3.6, 1.3.4, 4.1 – 4.3, 5.5 | детект дрейфа, канарейки по адаптерам, автопауза, экран здоровья |
| `1.0.0` **Релиз** | 5.1, 5.2, 5.6, 5.7, 5.8.1 | трей и автозапуск, полный редактор правил, приёмка, сборки под Windows и Linux |

Три решения в этой нарезке стоит объяснить, потому что каждое выглядит спорным.

**Морфология не в MVP-1.** Согласованный минимум — простые слова и маски.
Поэтому эпик `2.1` содержит только нормализацию и маски, а стеммер вынесен в
отдельный эпик `2.6`. Иначе состав среза расходился бы с составом эпика.

**Минимальный UI в MVP-1 обязателен.** Без эпика `5.0` пользователь не может ни
создать монитор, ни ввести токен бота — и срез перестаёт быть пользовательским.
Полный редактор `5.2` и настройки `5.4` потом расширяют эти же экраны.

**Поиск по описанию и кнопка «В избранное» — не в MVP-1.** Описание требует
фильтра продавца, который приходит в `0.4.0`; кнопка «В избранное» без
мониторинга цен из `0.5.0` была бы кнопкой без обещанного поведения.

**Схема БД создаётся по срезам, а не целиком.** Задачи `0.3.4`–`0.3.6` лежат в
фазе 0 по принадлежности, но выполняются вместе со своими потребителями:
`SellerBlock` нужен фильтру продавца в `0.4.0`, избранное и цены — в `0.5.0`,
журнал здоровья — в `0.6.0`. До появления `HealthEvent` события здоровья
пишутся в `Run`.

## Сколько это стоит

Честная оценка критического пути до `0.3.0`, по уже написанным карточкам плюс
прикидка по эпикам без карточек:

| Часть | Часы |
|-------|------|
| Фундамент (`0.1.0`) | 25 – 34 |
| Разведка контракта (`1.0`) | 3 – 5 |
| Ядро парсинга (1.1, 1.2, 1.3.1–1.3.3, 1.4) | 35 – 47 |
| Правила и планировщик (2.1, 2.2, 2.4) | 24 – 33 |
| Telegram (3.1, 3.2.1–3.2.3) | 13 – 19 |
| Минимальный UI (5.0) | 13 – 17 |
| Первый запуск (5.8.2) | 3 – 4 |
| **Итого до MVP-1** | **116 – 159** |

Оценка выросла со 102–137 после того, как эпики критического пути были
разложены на карточки: декомпозиция обычно вскрывает работу, которую прикидка
пропускает. Все задачи пути теперь имеют карточки, так что дальше цифра должна
уточняться фактом, а не пересмотром.

Это не двухнедельный объём, и называть его так было бы неправдой. Если нужен
именно двухнедельный результат, сокращать надо состав, а не оценку: самая
дорогая часть — фундамент, и большая часть его стоимости приходится на Docker,
Postgres и CI, то есть на инфраструктуру до первой пользовательской ценности.

## Следующие шаги

1. Фаза 0 целиком.
2. Эпик `1.0` — разведка контракта. Он выполняется **до** `1.1.1`: проектировать
   отображение адресов на API по догадкам нельзя.
3. Дальше по срезу `0.3.0` до первого уведомления в Telegram, затем остановиться
   и пересмотреть оставшиеся срезы по факту работы системы.
4. Карточки задач для эпиков за пределами критического пути генерируются перед
   стартом своего среза.
5. Интерфейс переносится из прототипов в порядке таблицы срезов выше, а не по
   набору готовых макетов. В MVP-1 входят только оболочка, настройка Telegram,
   создание правила, минимальный список правил и состояние первого запуска.
   Лента, избранное, архив, здоровье и доска наблюдения приходят позже.

- TDD для парсеров, матчера, лимитера, водяного знака
- После правок docs — `npm run docs:ops:refresh && npm run docs:ops:check`
